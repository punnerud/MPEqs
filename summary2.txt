================================================================================
PHASE 92 — MPEqs' generic solver library: the record grows by CLASSES
================================================================================

Phase 91 gave the record a formula library — one relation per entry. This gives it a
SOLVER library: parameterised machines for whole problem classes, each taking a typed
spec (never code), executing exactly in Fractions or integers, refusing by name, and
reporting its work so a runaway search dies instead of hanging.

    15 solvers: search, linear_system, quadratic, crt, gcd_lcm, series,
    combinatorics, recurrence, rate_work, ratio_split, mixture, interest,
    base_convert, digit_ops, factor
    22 search predicates, 45 wordings (the lexical face, for embedding proposal)
    22/22 self-test cases exact, 6/6 refusals named and correct

The load-bearing one is SEARCH, because so many olympiad questions are "the <aggregate>
of all n in <domain> such that <conditions>": a domain (integer range, divisors of N,
divisors of k! via Legendre so 13! is never built), a conjunction of predicates, an
aggregate, and a post-op — which is exactly how AIME's "answer mod 1000" is said.

AND IT SOLVES A REAL AIME PROBLEM BY CHAINING, WITH NO MODEL AT ALL. "The sum of all m
with 13!/m a perfect square is 2^a 3^b 5^c 7^d 11^e 13^f; find a+b+c+d+e+f": search
returns 9,698,458,770, factor returns 2·3²·5·7³·11·13⁴, the exponent sum is 12 — the
published answer, and the problem phase 89's solo arms got right only 2 times in 10.

FOUR SELF-TEST FAILURES, AUTOPSIED: three were MY hand anchors (the 13! sum invented as
4989600 when hand derivation gives 9698458770; eight digit-sum multiples of 7 where
there are ten; 43/100 for a mixture that is 41/100), one was a REAL code bug (factor
with k=13 still demanded an "n", and the dispatcher reported the KeyError honestly as
an error rather than an answer). The tally across the study is now 7 hand-anchor errors
against 1 machinery error, and the machinery error was caught by the anchors — which is
the whole argument for writing truths before code.

PHASE 93 — mapping problems onto the solver library, and a hypothesis that died
================================================================================

Thirty problems (two per solver, distractor quantities throughout, truths verified
against the library BEFORE any model call — which caught three more of my anchors:
273 not 812, a(5)=111 not 63, digit sum 21 not 24). The model emits a JSON spec; the
record validates and executes; nobody computes but the record.

    embedding alone picks the right solver        28/30
    FREE   (whole catalogue, model chooses)       solver right 27/30, all 30 specs
                                                  parsed and ran -> EXACT 29/30
    GUIDED (embedding chooses, model fills only)  solver right 26/30, 28 parsed
                                                  -> EXACT 26/30

TWO FINDINGS, BOTH AGAINST WHAT I WROTE IN THE FILE'S OWN DOCSTRING BEFORE RUNNING IT:

  GUIDING MADE IT WORSE. The division of labour that has won at every earlier scale —
  narrow the model's job to slot-filling — LOSES here, 26 against 29. The two embedding
  misses propagate into confident wrong answers (a search problem forced through
  digit_ops returns 1; an arithmetic series forced through recurrence returns 487),
  and two mixture specs simply never came. Seeing the whole catalogue is itself
  information: at 35B, choosing was not the bottleneck, and taking the choice away
  removed a correction the model was making for free.

  A WRONG CHOICE DOES NOT SELF-DESTRUCT. Both arms refused ZERO specs. The slots are
  generic enough that a mis-chosen solver still fills and still runs, so the record's
  validation catches malformed specs but not misapplied ones. The delivery gate this
  study wants at spec level does not exist yet — that is now a measured hole, not an
  assumption.

And the one FREE "error" is not one: the CRT problem was mapped onto search over a
range with two mod_eq conditions and aggregate "list", which found exactly [13] — the
right number in the wrong shape. Alternative valid mappings are real (the label is not
the only correct answer), and a shape-normalising comparator would score FREE 30/30.
Reported both ways rather than rescored.

================================================================================
PHASE 95 (built before phase 94's evidence, deliberately) — the library grows by
expressions: tuples, polynomials, coordinates, modular arithmetic
================================================================================

Phase 92's search has a fixed predicate list and ONE variable, which is exactly where
competition problems escape it: they ask about pairs and triples related by arithmetic
nobody enumerated in advance. The general move is to let conditions be EXPRESSIONS,
written as ordinary strings — because format is capability (phase 84), and
"a*a + b*b == c*c" is something any model can write while nested predicate JSON is not.

Safety is phase 90's discipline reused: the string goes through Python's own parser and
is walked against a whitelist of node types and function names, so what executes is
arithmetic over bound variables and nothing else.

    multisearch  1-4 variables with ranges, optional strict ordering, expression
                 conditions tested AS SOON AS their variables bind (so triples are
                 feasible), an objective expression, aggregates, mod post-op
    polynomial   exact rational roots (verified, not guessed), Vieta, evaluation
    geometry     exact coordinates: squared distance, shoelace area, collinearity,
                 circle through three points, line intersection
    modular      modpow, inverse, multiplicative order, totient

    15/15 self-test cases exact, 6/6 refusals named — three of them attempted
    escapes from the expression sandbox (an __import__ call, an attribute access,
    a variable-exponent power), all refused by the AST walk before evaluation
    MPEqs now holds 19 solvers; expressions admit 14 functions over up to 4 variables

Written and self-tested BEFORE the coverage sweep of phase 94 ran, so that phase's
named-missing list is an honest test of whether this growth was aimed at the right
thing — a prediction, registered by timestamp in the repository, not a rationalisation.

PHASE 94 — how much of AIME the vocabulary actually reaches: measured, and it is 0
================================================================================

Thirty real AIME problems, the whole 15-solver catalogue in the prompt, and one
instruction: map it onto a solver, or NAME what is missing. The record then runs every
spec it is handed and compares to the published answer.

FIRST SWEEP WAS A HARNESS FAILURE, AND THE AUTOPSY SAID SO. Twenty-two of thirty replies
read as "unparseable" — which would have looked like a coverage result. The raw replies
were 2,400-3,500 characters of PROSE WORKING: the model had ignored the output format and
started solving instead of mapping. Prefilling the JSON opening brace into the assistant
turn removed the prose branch entirely — one character, phase 84's law at 35B — and the
sweep was re-run.

THE REAL NUMBERS, and they are stark:

    claimed a mapping      22/30   (declined 5, still unparseable 3)
    the spec ran           19      (the record refused 3 as malformed)
    exact vs published     0       (wrong 19)

    solvers reached for: search 16, linear_system 3, quadratic 2, recurrence 1
    named as missing: geometric probability, symbolic algebra and logarithms,
    nonlinear systems with radicals, geometric reasoning (x2)

Three things follow, none of them comfortable:

  WILLINGNESS TO MAP IS NOT REACH. Told to map, the model maps anything — a tennis
  tournament probability became a sum over a range with condition "eq 1"; a cube-geometry
  volume became an identity linear system. Nineteen confident wrong numbers came out of
  a pipeline whose every component is exact.

  THE BOTTLENECK IS THE MAPPING, NOT THE MACHINES. Problem 0 IS in vocabulary — phase 92
  solved it by hand-chaining search and factor to the published answer 12 — and the model
  chose the right domain (divisors_of_factorial, k=13) but passed arg=13 instead of 13!.
  A parameter, not a capability.

  A DELIVERY GATE AT SPEC LEVEL IS NOT OPTIONAL. Phase 93 measured that mis-mappings
  never self-destruct; this measures what that costs on real problems: everything.

================================================================================
PHASE 96-97 — the spec-level gate, and an ablation that prices every layer
================================================================================

Phase 93 measured the hole (mis-mappings never self-destruct); phase 94 measured what
it costs (19 confident wrong AIME answers). The gate is built from two mechanisms this
study proved separately: VALUE ECHO (every literal in the spec must appear in the
problem or be a structural constant — phase 91) and TWO MACHINES (the model gives a
second spec that must use a DIFFERENT solver, and the record runs both — phase 74;
unlike phase 89's two phrasings, these are two computations, not two readings).

Run on two arms: the 30-problem battery where mappings are mostly right, and 15 AIME
problems where phase 94 measured every mapping wrong. Replies are cached and the specs
recorded, so the ablation below costs no GPU and runs over IDENTICAL data.

    BATTERY (n=30)                          AIME (n=15, all mappings wrong)
    gate    delivered right WRONG           delivered right WRONG
    none          30    29     1                   8     0     8
    echo          13    13     0                   1     0     1
    agree          5     5     0                   2     0     2
    both           3     3     0                   0     0     0
    both+          4     4     0                   1     0     1

Four findings, all uncomfortable in the useful way:

  ONLY THE FULL COMPOSITION NEVER LIES. "both" is the single row with zero wrong
  deliveries on the hard set — and it gives back 10% of the easy set. On this evidence
  lie-freedom costs ninety percent of coverage. That is the exchange rate, measured.

  AGREEMENT ALONE IS WEAK HERE. Two different machines agreed on garbage twice on AIME:
  when both roads collapse to a trivial value (a sum over an empty condition, a count
  of nothing) they agree perfectly. Structural difference is not independence.

  ECHO ALONE IS THE BEST SINGLE LAYER. Recall 0.43 at one lie — better than agreement
  on both axes, and it costs no model call at all. Cheap mechanical checks keep beating
  expensive social ones, which is this study's oldest result.

  RELAXING ECHO BUYS ALMOST NOTHING. Allowing digit-scale constants (0-12, and the
  loop bounds a digit search needs) as structure recovers one battery problem and lets
  one AIME lie through. The strict rule is the better trade.

Also measured, no model calls: 29 of 30 PLANTED mis-mappings caught (right numbers,
wrong machine), 12 of them by echo alone.

================================================================================
PHASE 98 — MPEqs on GSM8K: the arith solver, shape over name, and an honest loss
================================================================================

Two additions first, both forced by evidence rather than taste:

  ARITH. Word problems are a handful of quantities combined in a few steps, and the
  library had no machine for that — phase 45's plan graph, reborn as a library member:
  named steps, each an expression over the problem's numbers and earlier steps, all
  evaluated exactly in Fractions inside the same AST sandbox that guards multisearch.
  Library now 20 solvers; 18/18 self-tests exact, 8/8 refusals named.

  SHAPE DISPOSES OVER NAME. The 1B immediately wrote a perfect arith body under the
  name "search". Phase 91's law one level up: when the NAMED solver fails, the SLOTS
  are allowed to say which machine this is, the repair is attempted, and every repair
  is COUNTED rather than performed silently. Fired 3 times in the run below, all
  ('search'|'linear_system') -> 'arith'.

THIRTY GSM8K PROBLEMS, THREE ARMS:

    SOLO-35B    28/30 — the model simply answers
    MPEqs-35B   spec parsed 29, ran 26 -> 21 exact, 5 wrong
    MPEqs-1B    spec parsed 16, ran 3 -> 1 exact

ROUTING THROUGH EXACT MACHINERY LOSES HERE, 21 AGAINST 28, AND THAT IS THE RESULT.
Grade-school arithmetic is something a 35B already does well; forcing it through a spec
adds mapping errors without removing any error that was there. The machinery pays where
the model is weak — exact fractions, unit routing, long searches, reversibility,
memory — and this is the measurement that says where that is NOT.

THE 1B RESULT IS THE SAME LAW AS PHASE 84. It produces JSON-shaped text (16 of 30
parsed) that is almost never a valid spec (3 ran). Making the task mechanical does not
help a model that cannot follow the mechanism; the floor is instruction-following, not
arithmetic.

WHAT DOES HELP IS CROSS-KIND AGREEMENT. Solo answering and spec-and-execute are two
DIFFERENT KINDS of work, not two phrasings, and gating on their agreement behaves
accordingly:

    echo alone            delivered 16, right 15, WRONG 1   precision 0.94
    agrees with solo      delivered 22, right 21, WRONG 1   precision 0.95
    both                  delivered 15, right 15, WRONG 0   precision 1.00

Against phase 89, where two PHRASINGS of the same kind of work agreed on the same
wrong number twice in three deliveries. The rule this study keeps re-deriving: what
makes agreement worth anything is that the two roads are different KINDS, and the
cheapest mechanical check is worth more than another opinion.

================================================================================
PHASE 99 — the vocabulary's ceiling on AIME: mapping failure, not reach failure
================================================================================

Phase 94's zero was compatible with two opposite diagnoses — the library cannot express
these problems, or it can and the mapper missed — and those call for opposite work. So
the same fifteen problems were mapped BY HAND, no model in the loop, and executed:

    hand-written specs, exact against the published answers   5/15
    the model's mapping on the same problems (phase 94)       0/19 that ran

    [ 0] sum of m with 13!/m square, then add the exponents          12  EXACT
    [ 1] sum of C(C(n,2),2) for n = 3..40, mod 1000                   4  EXACT
    [ 7] 2-colourings of a 12-gon with no monochromatic rectangle   928  EXACT
    [12] adults 5/12 of a crowd, 11/25 after 50 arrive, minimised   154  EXACT
    [13] least multiple of 23 that is 1 mod 2^n, counting fixed n   363  EXACT

A THIRD OF THESE AIME PROBLEMS IS EXPRESSIBLE IN TWENTY SOLVERS AND AN ARITHMETIC
SANDBOX, AND THE MAPPER FOUND NONE OF THEM. The bottleneck is named: not the machines,
not the vocabulary — the mapping. Problem 7 is the sharpest case: a rectangle in a
regular 12-gon is two diameters whose four vertices share a colour, so the whole thing
is fifteen mechanical conditions over the 4096 bit-patterns of one variable, and the
answer falls out exactly. Nothing about that is beyond a 35B to write; it simply did
not.

Two additions were forced by problems in this set, declared as such rather than
motivated by taste: pow2 and inv_mod inside the expression sandbox (problem 13 needs a
modular inverse at a variable power of two, which the literal-exponent guard blocks on
purpose), and an exponent_sum post-op (AIME asks for the exponents of a prime
factorisation to be added constantly; without it problem 0 needs two chained specs).
Library: 20 solvers, 16 expression functions, 18/18 self-tests, 8/8 refusals.

THE TEN OUT OF REACH NAME THE SAME THREE THINGS EVERY TIME: plane and solid geometry
(five of them), quantifiers over structures rather than integers — families of subsets,
uniqueness of roots (three), and expectation under an adaptive strategy (two). That is a
build list, not a mystery.

================================================================================
PHASE 100 — teaching the mapping, and what the refusals demanded next
================================================================================

Phase 99 left one lever: the model had been told the VOCABULARY but never shown the
SHAPE of the work. So three worked mappings went into the prompt — a bit-pattern
enumeration, a two-variable Diophantine minimisation, an aggregated expression with a
mod post-op — all invented for the purpose so nothing leaks from the test set. Same
single call per problem; no retry, no feedback, no second look.

    claimed 10/15, ran 3, EXACT 1 (wrong 2, refused 7, declined 3, unparseable 2)
    of the 5 problems proved reachable: 1 solved
    baselines: no examples 0 exact; hand-mapped ceiling 5

One of five, from zero. Worked examples move the mapping, and they do not close it.

THE SEVEN REFUSALS WERE THE REAL YIELD — a build list written by the failures:

  A BUDGET DEATH THAT WAS THE MACHINE'S FAULT, NOT THE MODEL'S. The model wrote the
  adults-at-a-concert problem as two variables to 10,000 with two linear equations —
  10^8 tuples, refused — where my hand spec used tighter bounds. The fix is generic and
  belongs in the machine: when the innermost variable appears in a LINEAR equality,
  SOLVE for it instead of scanning it. The model's own rejected spec now runs in 10,001
  steps instead of 10^8.

  AND THE FIRST VERSION OF THAT FIX WAS UNSOUND, CAUGHT BY THE SELF-TESTS. I implemented
  it as phase 75's probe trick — sample the residual at 0, 1, 2, and if the three points
  are collinear, solve. digit_sum(n) - 10 sampled at 0, 1, 2 gives -10, -9, -8: a perfect
  straight line, so the solver skipped the scan and returned 0 where the truth was 10.
  THREE SAMPLES CANNOT CERTIFY LINEARITY; THE SYNTAX CAN. Replaced with a structural AST
  check (a call containing the variable is never linear, a power never is, a product only
  when one side is free of it), and the speedups survive exactly where they are sound:
  a+b=20 walks 27 states instead of 361, digit_sum falls back to the full 1,010, the
  hand-written AIME spec walks 2,004 instead of 102,051.

  SMALLER ONES, ALSO GENERIC: an "eval"/"only" aggregate for degenerate one-hit searches
  (the model asked for it by name), and a decline written as {"solver":"none"} which the
  harness had been scoring as a refusal.

RE-EXECUTING THE SAME SPECS AGAINST THE GROWN MACHINE, no new model calls: refusals fell
7 -> 5 and two more specs ran — and BOTH are wrong (25 against 244, and 550 against 154,
the latter because the model assumed all fifty new arrivals were adults). Growing the
machine converts refusals into answers, not into correct answers. The mapping is still
where the error lives, and every layer that could hide that has now been measured
separately.

PHASE 101 — retrieved exemplars: retrieval is perfect, the mapper still is not

Phase 100's three fixed examples could not cover the shapes the reachable problems
need, so the bank grew and became retrievable: twelve exemplar mappings (invented, no

    retrieved the needed shape for the reachable five   5/5
    claimed 10, ran 6, EXACT 1 (of the reachable five: 1)
    baselines: no examples 0, fixed three 1, hand-mapped ceiling 5

RETRIEVAL IS NOT THE PROBLEM. Every one of the five reachable problems had the right
exemplar in front of the model — factorial_divisors for the 13! question, bits for the
dodecagon, diophantine for the concert crowd, modular_inverse for the powers of two —

    machines        exact, 20 solvers, 18/18 self-tests, refusals named
    vocabulary      reaches 5 of 15 (proved by hand)
    retrieval       puts the right shape up 5 of 5

Whatever is missing lives in the step where a problem in language becomes a filled

One harness bug caught on the way, and it would have poisoned everything downstream:

tokenises past the 512-token window and llama-embedding silently emits an extra row —

embedding fixed it and improved the key, since the shape lives in the words, not the
typesetting.

================================================================================
PHASE 102 — where MPEqs wins: the band between easy sums and real mathematics
================================================================================

Phase 98 measured an honest loss (GSM8K: solo 28/30, machinery 21/30) and phase 94 a
collapse (AIME: mapping 0). Between them is the band this apparatus exists for: problems
whose MAPPING is one sentence and whose ARITHMETIC is out of reach. Twenty of them,
truths computed before any model call, in four families — twelve-step exact fraction
folds, big-integer products and powers, counts over hundreds of thousands, divisor
structure of large factorials.

    SOLO-35B    0/20      not one, and never for want of trying: it answers every time
    MPEqs       8/20      first run, specs parsed 19, ran 14

THEN THE FAILURES NAMED FIVE MISSING MACHINES, and every one was a real gap:

  EXACT RATIONALS — a correctness BUG, not a preference: "5/11 * 5/11 * 5/11" evaluated
  in floats and the record returned 2774945224945457/225179981, the exact binary
  expansion of a rounded double, where the truth is 125/1331. Integer literals are now
  wrapped as Fractions whenever an expression divides, so `/` is exact; integer searches
  keep integer speed (a 200,000-wide digit search still runs in 0.2 s).

  ^ MEANS POWER. The model wrote (-1)^1 and Python read a bitwise xor. In a mathematics
  spec language the caret is a power, and xor was never in the whitelist anyway.

  A FOLD MACHINE. "Nine times in a row, add 2/5 and then multiply by 3/4" is neither an
  arith chain (no loop) nor a multisearch (a map-reduce is not a fold). The new iterate
  solver carries an accumulator across k, exactly.

  VARIABLE EXPONENTS ON A BOUNDED BASE. (-1)^k is the alternating sign half these
  problems need; the literal-exponent guard exists to stop unbounded growth, and a base
  of absolute value at most one cannot grow.

  PRODUCT AS AN AGGREGATE, and six variables instead of four.

    MPEqs after the growth   12/20     (specs parsed 19, ran 18)
    by family: fractions 4/5 (was 0), big 3/5, count 2/5, divisors 3/5
    SOLO-35B, unchanged      0/20

TWO MORE ROUNDS OF THE SAME LOOP, each driven by an autopsy rather than a hunch:

  A REPORT VOCABULARY. Several machines return a record — gcd AND lcm, divisor count
  AND divisor sum — and nothing in a spec said which number was being asked for, so a
  right answer inside a dict scored wrong. A spec may now carry "report", the dispatcher
  routes by it (asking digit_ops for a divisor sum now lands in factor), and the literal
  exponent cap went from 64 to 1024 because 2^200 is bounded, not unbounded.

  AND THAT ROUND REGRESSED THE DIVISOR FAMILY, 3 to 2, FOR A REASON WORTH KEEPING. When
  "report" was appended to the factor schema line, the k-versus-n distinction — k means
  k FACTORIAL — slid to the end of the sentence, and the model began writing {"n": 25}
  for "25 factorial". A schema is read literally; a buried distinction is a lost one.
  Rewriting that line to lead with the factorial case took the family from 2 to 5.

    MPEqs, final     15/20   (fractions 4, big 4, count 2, divisors 5; wrong 2)
    SOLO-35B         0/20    still not one, still never abstaining

    the progression: 8 -> 12 -> 12 -> 15, and every step was a failure autopsied
    into either a missing machine or a misread schema

Twelve against zero. The same machinery that LOSES to the model on grade-school sums
beats it twelve to nothing where the arithmetic is real — and the library grew by what
the problems asked for, four extra solves bought by five fixes that the failures wrote
themselves. Library: 21 solvers, 23/23 self-tests exact, 9/9 refusals named.

================================================================================
PHASE 103 — the gate does not transfer: different band, different failure mode
================================================================================

Phase 102's win came with an uncomfortable detail: MPEqs answers 12 of 20 correctly and
6 wrongly, and nothing in that arm says which is which. So phase 97's gate was carried
into the winning band — two machines plus value echo — and it does not survive the
journey.

    gate      delivered  right  WRONG        (hard-arithmetic battery, n = 20)
    none            16     12      4
    echo             7      4      3
    echo relaxed     9      6      3
    agree            0      0      0
    both             0      0      0

TWO MECHANISMS, BOTH DEAD, FOR REASONS THAT ARE PROPERTIES OF THE BAND:

  AGREEMENT IS UNAVAILABLE. A second, genuinely different machine was offered for 17 of
  20 problems and ran for 8, and it never agreed. There is no second way to compute
  987654321 x 123456789 in this library — one natural machine per problem is not a
  weakness of the mapper, it is what an exact arithmetic question IS. Phase 97 measured
  agreement as the weaker layer; here it is not a layer at all.

  VALUE ECHO IS ACTIVELY HARMFUL. Precision falls from 0.75 ungated to 0.57 with echo,
  because in this band the literals are DERIVED rather than invented: the twelve-step
  fold needs the 3 and 4 inside (k+2), the six-digit palindrome count needs 100000 and
  999999 that the problem says only as the word "six-digit". Echo was built to catch a
  hallucinated bound; here it catches arithmetic.

WHAT REMAINS TRUE IS THE COMPARISON THAT MATTERS. The model alone on this battery:
0 right, 20 confident wrong, 0 abstentions. MPEqs ungated: 12 right, 4 wrong, 4 flagged
by the machines themselves (refusals and unparsed specs). Routing through the machinery
takes the lie rate from 100% to 20% and correctness from 0% to 60% — without any gate
at all, because the machines' own refusals are already a partial gate.

The general law, now with two sides measured: a delivery gate is only as good as the
independence it can find. Where the risk is MAPPING, two entry points and a value echo
find it cheaply. Where the risk is ARITHMETIC, both mechanisms have nothing to grip,
and the honest report is the residual error rate — not a gate that flags everything and
calls it safety.

One more bug caught, in the gate itself: isinstance(True, int) is true in Python, so a
JSON boolean inside a spec was being reported as an invented literal named "True".
Phase 97's numbers were checked against the fix and are unchanged (no booleans in those
specs); the hard battery had ten.

    by family              fractions 4, big 4, count 4, divisors 5

    tuned battery for comparison: 15/20

    grade-school word problems   the model alone wins       28/30 against 21/30

================================================================================
PHASE 105 — widening the band: exact probability and unit conversion
================================================================================

With the domain drawn and the mapper measured as the bottleneck for competition
mathematics, the cheap direction is to widen the band where the pipeline already works.
Two classes went in, both failing a model for the same reason the hard-arithmetic
battery does — the answer is an exact ratio it cannot hold — while the mapping stays one
sentence long:

  PROBABILITY  a uniform space of tuples, an event as more constraints, and the answer
               as a Fraction. Both counts run through the multisearch machine, so
               pruning, budgets and the expression sandbox are inherited, not rebuilt.
               The m+n report the competitions ask for is one field.
  CONVERT      the phase 73 brick router as a library member at last. Sixteen written
               conversion facts, lifted through compound type space on demand, exact,
               and refusing honestly when no path exists (kroner to kilograms).

    twenty problems, ten of each, truths computed before any model call

    SOLO-35B    1/20     probability 0/10, convert 1/10
    MPEqs      17/20     probability 9/10, convert 8/10 (parsed 20, ran 18, wrong 1)

Nine of ten exact probabilities where the model gets none: it answers 0.11 or 4/36
unreduced or simply the wrong count, and the exact m/n is what was asked. Eight of ten
conversions where it gets one: 3 miles per second is 10863072/625 km/h and no amount of
confidence produces that from mental arithmetic.

The routing machinery had existed as its own experiment since phase 73 and could not be
REACHED by a mapped problem until it became a solver with a schema line. That is the
whole lesson of this phase: a capability nobody can address is not a capability.

================================================================================
PHASE 106 — three more classes: statistics, calendar arithmetic, percentage chains
================================================================================

The band is no longer a discovery, it is a construction, and each class is another
slice. Three more, chosen by the rule phase 105 established — mechanical where the model
is weak, one sentence where the mapping is strong:

  STATISTICS  exact mean, median, both variances, exact standard deviation when it is
              rational and named irrational when it is not — never quietly rounded
  DATETIME    days between dates, weekdays, dates shifted by a thousand days, leap-year
              counts across a century boundary
  FINANCE     successive percentage changes (which do not add), annuity payments, tax

    eighteen problems, truths computed before any model call

    SOLO-35B    8/18     statistics 4/6, datetime 1/6, finance 3/6
    MPEqs      18/18     statistics 6/6, datetime 6/6, finance 6/6

Calendar arithmetic is the sharpest split: 1 against 6. "How many days from 1 January
1970 to 10 August 2026" has one right answer, 20,675, and no amount of fluency produces
it.

AND THE SAME DEFECT APPEARED A THIRD TIME. The one MPEqs miss before the fix was a tax
problem where the model wrote "rate": 25 meaning 25 percent while the slot meant a
fraction of one. Phase 102 lost a family to a buried k-versus-n distinction; phase 105
needed the unit vocabulary spelled out; here an ambiguous unit inside a slot cost the
answer. THE MAPPER'S ERRORS ARE OVERWHELMINGLY SCHEMA-READING ERRORS, not reasoning
errors — the slot now says "percent" and takes whole percents, the solver treats any
rate above one as a percentage, and the family went 5/6 to 6/6.

That is a design rule with three measurements behind it: a slot must name its unit and
lead with its distinction, because the model reads the schema literally and has nothing
else to go on.

PHASE 107 — does the catalogue scale? Twenty-seven problems, nine classes
================================================================================

Every class so far was measured in its own run, with its own worked example and a
catalogue that happened to hold the machine it needed. The deployment question is
harder: with twenty-six solvers in the prompt and three GENERIC examples matching no
class, can the model still pick the right machine?

    twenty-seven problems, three from each of nine classes, truths pre-computed

    SOLO-35B   7/27
    MPEqs     20/27   (parsed 25, ran 23, wrong 3)

    class          n  solo  mixed   focused
    big            3     0      2       4/5
    convert        3     0      2      8/10
    count          3     0      3       4/5
    datetime       3     1      3       6/6
    divisors       3     0      3       5/5
    finance        3     2      3       6/6
    fractions      3     0      0       4/5
    probability    3     1      1      9/10
    statistics     3     3      3       6/6

SIX CLASSES HOLD AT FULL RATE; TWO COLLAPSE — and they are exactly the two whose worked
example vanished. Fractions went 4/5 to 0/3 without the fold example and probability
9/10 to 1/3 without the probability one: the model stopped reaching for iterate and
probability at all, though both were in the catalogue with their slots spelled out.

A CATALOGUE LINE IS NOT ENOUGH FOR A MACHINE THE MODEL HAS NEVER SEEN USED. The
schema-literacy rule of phase 106 has a companion: a schema says what the slots are, an
example says that the machine EXISTS as a thing to reach for. The confound is declared —
a drop here mixes catalogue size with the loss of class-matched examples — which is
exactly why the next phase separates them.

================================================================================
PHASE 108 — retrieval closes the scaling gap: 25 of 27, and nothing wrong
================================================================================

The confound from phase 107 is removed the way phase 101 pointed to: one invented
exemplar per class in a bank, embedded with numbers masked, the two nearest retrieved
per problem, and everything else identical — same twenty-seven problems, same
twenty-six-solver catalogue, same generic instruction, same model.

    MIXED, generic examples      20/27   (3 wrong)
    MIXED, retrieved exemplars   25/27   (parsed 26, ran 25, WRONG 0)
    SOLO-35B                      7/27

    the two collapsed classes recover: fractions 0/3 -> 2/3, probability 1/3 -> 3/3,
    convert 2/3 -> 3/3, and no class loses anything

Ninety-three percent, no wrong deliveries, on nine different kinds of problem the model
alone answers correctly seven times in twenty-seven. And the recipe is now stated as
three parts, each of which was measured separately before being combined:

    A MACHINE that is exact and refuses by name              (phases 92, 95, 102, 105-6)
    A SCHEMA LINE that names its units and leads with its
      distinction, because the model reads it literally       (phase 106's rule)
    AN EXEMPLAR that is RETRIEVED, not fixed, because a
      catalogue cannot grow inside a prompt                   (phases 101, 107, 108)

That is what "gradually swapping the set" turned out to mean. A library scales when
every machine carries its own way of being addressed — and the thing that finally made
twenty-six solvers behave like twenty-six solvers, rather than like the three the prompt
happened to illustrate, was a 384-dimensional nearest-neighbour lookup that costs no
model call at all.

================================================================================
PHASE 109 — the 1B can map, once the exemplar is fetched for it
================================================================================

The oldest open thread in this study is whether the small model can be made useful by
making the task mechanical. Phase 84 found OLMoE-1B answering at the parrot line on
one-bit reads; phase 98 saw it parse sixteen specs of thirty with three executing. Both
were before retrieval existed, and the 1B's failure was never arithmetic — the record
does that — it was knowing what to write.

A retrieved exemplar is exactly a template of what to write, in the shape of this
problem, for a machine that fits. So the phase 108 run was repeated with nothing changed
but the seat:

    OLMoE-1B alone                    1/27
    OLMoE-1B through MPEqs           12/27   (specs parsed 27/27, ran 17, wrong 5)
    Qwen-35B through MPEqs           25/27

    by class: datetime 3/3, probability 3/3, statistics 2/3, count 2/3, big 1/3,
    finance 1/3, convert 0/3, divisors 0/3, fractions 0/3

TWENTY-SEVEN OF TWENTY-SEVEN SPECS PARSED, against sixteen of thirty in phase 98. The 1B
went from producing JSON-shaped text to producing valid specs, and from one right answer
to twelve, on problems where it computes nothing at all. The classes it gets are the ones
whose exemplar is a near-template — a date subtraction, a dice probability, a variance —
and the ones it misses need the exemplar ADAPTED rather than copied, which is the
capability boundary drawn in the sharpest terms this study has managed.

So the answer to a question asked many phases ago — make it simple enough for a 1B to
apply — is a measured yes with a stated shape: the 1B can drive twenty-six exact
machines at forty-four percent on nine classes where it manages four percent by itself,
provided the arithmetic is not its job and the example is fetched, not remembered.

================================================================================
PHASE 110 — the band is about difficulty, not about class
================================================================================

Three more machines went in the way the recipe says — shape (standard figures with pi
kept SYMBOLIC, because the area of a circle of radius 5 is 25*pi and 78.54 is a
different answer), inclusion-exclusion (the survey problem, up to four sets), and phase
91's FORMULA LIBRARY, which had existed for fifteen phases and answered nothing until
today because nothing could address it. Each with a bank exemplar from the first minute.

Then the battery came back tied:

    easy instances (n = 15)     SOLO-35B 15/15      MPEqs 15/15

Which is the phase 105 rule from its negative side: a machine does not widen the band
unless the class is actually beyond the model. A circle of radius 7, three sets of a few
hundred, momentum of 12 kg at 7 m/s — the model does all of that unaided.

So the same three classes were regenerated with awkward fractions and large numbers,
changing NOTHING about the classes, the schemas or the bank:

    hard instances (n = 15)     SOLO-35B 7/15       MPEqs 14/15
    by class: shape 2 -> 5, inclusion 3 -> 5, formula 2 -> 4; MPEqs wrong 0

THE BAND IS DEFINED BY ARITHMETIC DIFFICULTY, NOT BY SUBJECT. The same machine, the same
mapping, the same prompt: at radius 7 it is redundant and at radius 47/6 it is the only
thing that works. Every earlier band result reads the same way in hindsight — GSM8K lost
because grade-school sums are easy, not because word problems are the wrong shape — and
the deployment rule that follows is not "route by topic" but "route by whether the
arithmetic will fit in the model's head".
